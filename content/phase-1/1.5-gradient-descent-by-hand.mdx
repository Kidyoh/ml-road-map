    answer_key: >-
      The gradient is 2x, so the update is x_next = x - lr * 2x = x(1 - 2*lr).
      Each step multiplies x by the fixed factor (1 - 2*lr), so the behaviour is
      determined entirely by that factor's magnitude. If it is less than 1 in
      absolute value, x shrinks geometrically and converges; if it equals 1 in
      absolute value, x keeps its magnitude forever; if it exceeds 1, x grows
      without bound. Solving |1 - 2*lr| < 1 gives 0 < lr < 1, with lr = 0.5 the
      fastest possible since it makes the factor zero and lands on the minimum in
      a single step. At lr = 1 exactly the factor is -1, which is why the value
      flips between 1 and -1 forever. The general condition: for a quadratic, the
      curvature is the second derivative, and gradient descent is stable when lr
      is below 2 divided by the largest eigenvalue of the Hessian. Here the
      Hessian is just 2, so the bound is 1. This is the same rule that governs the

      explodes or crawls, and neither looks like a working algorithm.

## Why this node exists

Gradient descent is three lines of code. Understanding why it fails is the actual
content, and it fails in two very different ways that look identical from the
outside.

The first is a learning rate too large for the curvature: the loss explodes and
you see NaN. That one is loud. The second is a badly conditioned problem, where
no single learning rate is both stable and useful, and the symptom is a run that
seems to work but goes nowhere. Appendix B of the build plan names this exactly:
*not normalizing features, then blaming the algorithm*.

By the end of this node you should reach for a histogram of your feature scales
before you reach for the learning rate.

## The session

### 1. The simplest possible case

`f(x) = x^2`, starting at `x = 1`. The gradient is `2x`.

```python
def descend(lr, steps=50, x=1.0):
    history = [x]
    for _ in range(steps):
        x = x - lr * 2 * x
        history.append(x)
    return history
```

Run it at `lr = 0.1`, `0.5`, `1.0`, `1.01` and `10.0`.

| lr | after 50 steps |
|---|---|
| 0.1 | 1.4e-05 — converging |
| 0.5 | exactly 0.0 — one step to the minimum |
| 1.0 | 1.0 — oscillating forever between 1 and -1 |
| 1.01 | 2.7 — slowly diverging |
| 10.0 | overflow — diverged within 15 steps |

**The lr = 10 run is required by the checklist.** Print the sequence and watch it
grow. Appendix B asks for it specifically, because reading "it diverges" and
seeing 1, -19, 361, -6859 are not the same experience.

Then derive the boundary. `x_next = x(1 - 2*lr)`, so stability needs
`|1 - 2*lr| < 1`. Question 1 asks you for this.

### 2. The scaling trap

[`scaling-trap.csv`](/datasets/scaling-trap.csv) — 2,000 rows, two features, one
target. Nothing is missing, nothing is dirty. The only problem is scale:

| | standard deviation |
|---|---|
| x1 | 0.979 |
| x2 | 19,408 |

Fit `y = b + w1*x1 + w2*x2` with your own gradient descent. No sklearn.

First get the answer the easy way, so you know what you are aiming at:

```python
beta = np.linalg.lstsq(np.c_[np.ones(len(X)), X], y, rcond=None)[0]
# intercept 11.9591, w1 3.0061, w2 0.00040077
```

Now try gradient descent on the raw features. Start at `lr = 0.01`. It will
explode. Try `1e-5`. It will explode. Keep going.

The largest stable learning rate is about **6.9e-10**. Find a value that works
and one that does not, either side of it. Notice how useless the working one is —
after a thousand steps you have barely moved.

### 3. Fix it in one line

```python
Z = (X - X.mean(axis=0)) / X.std(axis=0)
```

Now run gradient descent at `lr = 0.1`. It converges in under 200 steps.

The standardized coefficients come out near intercept 31.97, w1 2.944, w2 7.778.
Convert them back to raw units and check against the closed-form answer.

That conversion is the checklist item most people skip and the one that proves
you understood what standardizing did.

### 4. Watch the loss

Record the loss at every step of the working run and plot it. It should decrease
monotonically — plain full-batch gradient descent below the stability threshold
never increases the loss. If yours does, your learning rate is above the bound
even though it has not visibly exploded yet.

## Why the threshold is what it is

For a least-squares problem the curvature is captured by the Gram matrix
`X.T @ X / n`. Gradient descent is stable when

```
lr < 2 / largest eigenvalue
```

For the raw features that largest eigenvalue is about **2.887e9**, giving a bound
of 6.928e-10 — which is exactly what you found empirically. After standardizing,
the eigenvalues fall between about 0.94 and 1.06 (numpy's `eigvalsh` puts the
condition number of the raw problem near 2.2e10 and the standardized one near
1.1), so the bound moves to about 1.895 and any sensible learning rate works.

Conditioning is a property of your data. The optimizer is downstream of it.

## Common walls

**Your gradient has the wrong sign and the loss climbs steadily.** The gradient
points uphill; descent subtracts it. If your loss rises smoothly rather than
exploding, check the sign before the learning rate.

**You forgot the 1/n in the mean squared error gradient.** It still converges,
just with an effective learning rate scaled by the number of samples — which
means your learning rate is 2,000 times larger than you think it is. Be
consistent between loss and gradient.

**You standardized the target as well and your intercept looks wrong.** That is
legitimate, but you have to undo it too. Simplest is to leave y alone.

**You standardized using statistics from the whole dataset.** Correct here, since
there is no split. It will be wrong the moment there is one — that is node 2.3,
and it is the second of its three leaks.

**Your converted coefficients are close but not exact.** Check the intercept
conversion: it is not just a rescale, it also has to absorb the subtracted means,
`b_raw = b_std - sum(w_std_i * mean_i / sd_i)`.
