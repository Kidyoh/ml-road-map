      rows for that customer, you get 3 times 2 equals 6 rows out. Pandas is doing
      exactly what a SQL join does and has no way to know you assumed the right
      table was one row per customer, so it says nothing. Here 120 customers have
      2 rows each in the dimension table, and the 1,071 extra rows are the
      transactions belonging to those 120 customers, counted a second time. The
      one-line check is to assert the join key is unique on the side you are

    answer_key: >-
      Row-by-row inference makes each date independently ambiguous: 06/03/2024 is
      valid as both the 6th of March and the 3rd of June, so pandas picks one, and
      for dates where the day exceeds 12 it is forced into the other reading. You
      end up with a column where some dates are day-first and some are month-first
      and nothing distinguishes them afterwards. Detection is by distribution, not
      by inspection: plot a histogram of the parsed day-of-month, or of the month.
      If the format is being mixed up, you see a discontinuity at 12 — the first
      twelve values of one field are inflated because they absorbed the values
      that should have gone to the other. Any real date column should be roughly
      uniform across days of the month; a cliff at 12 is a parsing bug with a
      signature. The fix is to parse each format explicitly rather than letting
      anything infer, and to assert afterwards that no values are NaT.

## Why this node exists

Node 0.2 gave you fast operations over clean arrays. Real data is not clean, and
the gap between "I know the pandas API" and "I can be trusted with a CSV" is
almost entirely about noticing when something silently went wrong.

Everything in this dataset is a real failure that has shipped to a real dashboard
somewhere. None of it raises an exception.

## The data

Two files:

- [`messy-transactions.csv`](/datasets/messy-transactions.csv) — 8,432 rows of
  transactions, one row per transaction, except where it is not.
- [`customers.csv`](/datasets/customers.csv) — a customer dimension table with
  segment and region.

What is wrong with them, stated plainly so you spend your time fixing rather than
guessing:

| Problem | Where |
|---|---|
| Exact duplicate rows | `messy-transactions.csv` |
| Money stored as strings, three different ways | `amount` |
| Leading and trailing whitespace in a join key | `customer_id` |
| Four date formats in one column | `order_date` |
| Inconsistent casing and stray spaces | `channel` |
| Missing values written five different ways | `quantity` |
| Duplicated keys in a dimension table | `customers.csv` |

The slash-separated dates are **day first**: `06/03/2024` is the 6th of March. You
are being told this because inferring it is a different lesson; question 3 asks you
what you would have done without being told.

Missing values in `quantity` appear as empty strings, `NA`, `N/A`, `null` and a
field containing only spaces. `pd.read_csv` recognises some of these and not
others out of the box.

## The session

Get from the raw files to a dataframe you would put your name on, and report total
revenue.

Do it in this order and **write down the row count after every step**:

1. Load. Row count?
2. Drop exact duplicate rows. Row count? Did it change by the amount you expected?
3. Strip whitespace from `customer_id`. How many distinct customers now — and how
   many before?
4. Parse `amount` into a real float. Assert the dtype afterwards.
5. Parse `order_date`. Assert zero `NaT` afterwards.
6. Normalise `channel`. How many distinct values?
7. Merge in `customers.csv`. **Row count?**
8. Fix whatever step 7 did.
9. Sum `amount`.

Step 7 is the one. Everything before it is tedium; step 7 is the node.

## The discipline being taught

```python
def check(df, label, expected_rows=None):
    print(f"{label:<28} {len(df):>7,} rows")
    if expected_rows is not None:
        assert len(df) == expected_rows, f"expected {expected_rows}, got {len(df)}"
    return df
```

Call it after every step. Predict the number **before** you run the cell. Being
surprised is the signal — if you only look at the count after the fact, you will
rationalise whatever it says.

This is the same habit that catches leakage in node 2.3, and the same habit that
catches a broken preprocessing step in production three years from now. It costs
one line.

## Common walls

**Your deduped count is not 8,000.** Check whether you deduplicated on the full row
or on `transaction_id`. Here they give the same answer, which is a coincidence
worth understanding — the duplicated rows are verbatim copies. In most real data
they differ, and which one you want is a question about what a duplicate means in
your domain.

**Total revenue is slightly off.** Either you are summing before deduplication, or
after the merge inflated the rows, or your string-to-float parse silently dropped
the currency-formatted values. Check `df.amount.isna().sum()` and check your row
count.

**You cannot get the channel count down to 3.** Strip, then lowercase, in that
order. `" WEB "` and `"Web"` and `"web"` are one value.

**The merge count is right but the totals are wrong.** You may have deduplicated
`customers.csv` with `drop_duplicates()`, which does nothing here — the duplicated
customer rows differ in `region`, so they are not exact duplicates. You have to
decide which row wins. There is no automatic answer, and noticing that there is no
automatic answer is the point.
