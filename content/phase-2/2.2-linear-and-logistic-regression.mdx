  - prompt: "The standardized coefficient on recency is -1.58 and exp(-1.58) is 0.205. State precisely what that means, and then say why the unstandardized coefficient would have been useless for this purpose."
    answer_key: >-
      Logistic regression is linear in the log-odds, so a coefficient is the
      change in log-odds per unit change in the feature, holding the others
      fixed. Exponentiating turns that into an odds ratio: for each one standard
      deviation increase in recency — about 65 days here — the odds of returning
      are multiplied by 0.205, roughly a fifth. Longer since last purchase, much
      lower odds of coming back, which is the direction anybody would guess and
      the magnitude nobody would have guessed. The unstandardized coefficient
      would express the same relationship per single day rather than per standard
      deviation, giving a number very close to 1.0 per day that looks negligible
      and is not, exactly as node 1.5 showed with the 0.0004 weight. Worse, it
      would be incomparable with the coefficient on monetary value, which is
      measured in currency. Standardizing first is what makes the coefficients
      comparable at all, and it is the only version worth reading as importance.
  - prompt: "Duplicating a feature column left the AUC unchanged but made the coefficients unstable. Explain the mechanism, and say what you would look for in a real dataset where the duplication is not exact."
    answer_key: >-
      With two identical columns, any split of the original coefficient between
      them produces exactly the same predictions — the model is unidentified, and
      which particular split you get depends on the solver, the regularisation and
      the random state rather than on the data. The predictions, and therefore the
      AUC, are unaffected, which is what makes this so easy to miss: nothing looks
      wrong except the interpretation. In real data the duplication is nearly
      never exact; it is two features that measure almost the same thing, such as
      total spend and transaction count times average basket, or height in
      centimetres and in inches after a unit fix. The symptoms to look for are
      large coefficients with opposite signs on related features, coefficients
      that swing wildly when you refit on a bootstrap sample or change the random
      seed, and a variance inflation factor above about 5 or 10. The fixes are to
      drop one, combine them, or use L2 regularisation, which resolves the tie by
      splitting the weight evenly and is the reason ridge is the sane default.
  - prompt: "Your linear regression predicting post-cutoff spend has residuals that violate the assumptions of ordinary least squares. Name two of those violations concretely, and say what each one breaks — being specific about whether it breaks the predictions or only the inference."
    answer_key: >-
      First, heteroscedasticity: spend is bounded below by zero and highly skewed,
      so the residual spread grows with the fitted value — customers predicted to
      spend a little are wrong by a little, customers predicted to spend a lot are
      wrong by a lot. This does not bias the coefficients, but it invalidates the
      standard errors, so any p-value or confidence interval on those coefficients
      is wrong. Second, the residuals are not normally distributed and cannot be:
      a large share of customers spend exactly zero, so the outcome has a point
      mass at zero and a long right tail, and no symmetric error distribution can
      describe that. This breaks inference for the same reason and also makes the
      squared-error loss a poor match, since it pulls the fit toward the extreme
      values. Predictions themselves can still be usable — least squares is the
      best linear unbiased estimator under weaker conditions than normality — but
      the honest fixes here are to model log spend, or to split the problem into a
      classifier for whether they spend at all and a regressor for how much given
      that they do.

## Why this node exists

Linear models are the baseline you will compare everything against for the rest
of the roadmap, and they are the model you should ship unless something else
earns its place. They are also the last model whose coefficients you can read
directly, which makes them the right place to learn what a coefficient is and
what it is not.

This node also delivers a result that is more useful than a good one: the model
you carefully build is going to tie with a single sorted column. That happens
constantly in practice and almost never in tutorials.

## The session

Pick up exactly where node 2.1 left off — same population, same cutoff, same
label.

### 1. Build the feature table

From transactions strictly before 2024-10-01:

```python
g = pre.groupby("customer_id")
X = pd.DataFrame({
    "recency":   (CUTOFF - g.order_date.max()).dt.days,
    "frequency": g.size(),
    "monetary":  g.amount.sum(),
})
X["avg_basket"] = X.monetary / X.frequency
X["tenure"]     = (CUTOFF - g.order_date.min()).dt.days
```

Shape should be (2756, 5), base rate 0.5624.

### 2. Fit it properly

Standardize inside a pipeline, not before it. You are about to spend node 2.3 on
why, and there is no reason to build the bad habit first.

```python
pipe = Pipeline([("s", StandardScaler()), ("m", LogisticRegression(max_iter=2000))])
cross_val_score(pipe, X, y, cv=5, scoring="roc_auc")
```

**0.8387**, with a standard deviation of about 0.023.

### 3. Now the uncomfortable comparison

| Model | 5-fold CV ROC AUC |
|---|---|
| Recency, sorted (node 2.1's baseline) | 0.8376 |
| Logistic regression, recency only | 0.8381 |
| Logistic regression, all five features | **0.8387** |

Four extra features bought you 0.0006 AUC — a fifth of the standard deviation
across folds, which is to say nothing at all.

Sit with that before moving on. Question 1 asks you to write the report sentence.

### 4. Read the coefficients

```
recency      -1.5836
frequency    -0.1150
monetary     +0.1209
avg_basket   -0.0875
tenure       +0.1393
intercept    +0.1821
```

One feature is doing everything. `exp(-1.5836) = 0.2052`: each standard deviation
of extra recency multiplies the odds of returning by about a fifth.

Then refit **without** standardizing and compare. The AUC is identical; the
coefficients are unrecognisable. That is the whole argument for standardizing
before you interpret.

### 5. Break it on purpose

Add `X["recency_copy"] = X["recency"]` and refit several times with different
`random_state` values. Watch the coefficients on the pair move around while the
AUC does not budge.

Then add a small amount of noise to the copy instead of duplicating exactly, and
watch the same thing happen more subtly. That is what collinearity looks like in
real data.

### 6. Linear regression, and the assumptions it makes

Fit an ordinary least squares model predicting total post-cutoff spend. Plot the
residuals against the fitted values.

You will see a fan shape and a wall at zero. Both are assumption violations, and
question 4 asks you which parts of your conclusions they invalidate — the answer
is not "all of them".

## Logistic regression, in one box

It is linear regression on the log-odds:

```
log(p / (1 - p)) = b + w1*x1 + w2*x2 + ...
p = sigmoid(b + w1*x1 + ...)
```

That sigmoid is the same function you differentiated by hand in node 1.2, and the
optimizer sklearn uses is a more careful relative of the gradient descent you
wrote in node 1.5. Nothing new has been introduced — it has been packaged.

## Common walls

**Your AUC is around 0.16.** Sign flip. See node 2.1.

**Convergence warnings.** Raise `max_iter`, and check that you are standardizing —
the default solver struggles badly on unscaled features, which is node 1.5's
conditioning lesson appearing in a library.

**Your accuracy is 0.77 and you are pleased.** Against a majority-class baseline
of 0.5624, that is a real improvement, but accuracy is a poor choice here and
node 2.4 is about why. Report AUC.

**Your `avg_basket` has infinities.** Some customer has zero transactions in your
grouping, which means your population filter is not matching your feature table.
Both should be the 2,756 customers with pre-cutoff activity.

**You standardized before splitting.** It will not change these numbers
noticeably, and it is still wrong. Node 2.3 is next, and it exists for this.
