      their own feature values. The train and test sets are equally poisoned, so
      they agree beautifully. That agreement is the trap — it reads as evidence of
      a robust model and is in fact evidence of nothing. Held-out sets catch
      variance; they do not catch bias in how the features were constructed. The
      only defences against this class of problem are structural: build every
      transformation inside the pipeline so it can only ever see training folds,
      and ask of every column "when, in real time, does this value become known,

## Why this node exists

This is the highest-value node in the roadmap.

Everything up to here has been about building models. This node is about the
single most common reason a model that looked excellent in a notebook does
nothing in production. It is not a subtle statistical effect. It is a category of
bookkeeping error that is invisible, produces no warnings, and makes your work
look *better* — which is exactly why it survives review.

You are going to watch a 0.9966 become a 0.7497 and you are going to be pleased
about it. If you are not pleased about it, this node has not landed yet.

## The session

Download [`leaky-churn.csv`](/datasets/leaky-churn.csv) and
[`leaky_pipeline.py`](/datasets/leaky_pipeline.py) into the same folder.

```bash
pip install pandas scikit-learn
python leaky_pipeline.py
```

You should see:

```
cross-validated ROC AUC: 0.9966  (+/- 0.0016)
held-out ROC AUC:        0.9968
gap:                     0.0002
```

**Stop here and sit with that for a minute before reading on.** A five-fold CV
score of 0.9966 with a standard deviation of 0.0016, confirmed by a held-out set
to within two ten-thousandths. Every diagnostic you have been taught to run says
this model is excellent and stable.

There are three leaks. Find them, fix them, and report the honest number.

The dataset is 6,000 customers, 11 columns, 1,640 of them churned — a base rate
of 27.3%.

### Rules for the session

- You may not use the score to find the leaks. Read the code and read the column
  names. The metric is the thing under suspicion.
- Fix all three before re-scoring. Question 4 is about why.
- No new features, no model changes, no hyperparameter tuning. The only thing
  that changes is *when* each transformation gets to see data.

## The thing to have in your head

For every column, ask one question:

> At the moment I would actually need this prediction, has this value been
> written yet?

Not "is this correlated with the target". Not "does this seem fair". **When does
this value become known.** A column that is updated after the outcome occurs is a
leak even when it also contains real, legitimate signal.

And for every transformation, ask the same question a different way:

> Which rows did this transformation get to look at when it was fitted?

If the answer includes any row that will later be scored as validation or test,
the transformation is leaking, whether or not the number moves.

## What each leak is worth

Once you have your own answer, this is what we measured. Do not read this table
before you have three fixes of your own.

<details>
<summary>Ablation — open after you have fixed all three</summary>

| What is fixed | CV ROC AUC |
|---|---|
| Nothing (the starter script) | 0.9966 |
| Only the scaler | 0.9966 |
| Only the promo encoding | 0.9952 |
| Only dropping `days_since_last_login` | 0.8675 |
| Promo encoding and scaler, login kept | 0.9955 |
| All three | **0.7495** |

Three things worth staring at.

**The scaler fix is worth zero.** Not "small" — zero, to four decimal places. It
is still unambiguously wrong, and with a different model or a test set drawn from
a later period it would matter. A leak that costs nothing today is still a leak.

**Fixing one at a time tells you nothing.** With the login column present, the
model reaches 0.99 on that column alone, so removing another leak costs it
nothing — it just leans harder on what is left. If you had hunted leaks by
ablating and watching the score, you would have declared two of the three
innocent.

**The promo encoding is worth 0.118 AUC — but only once the login leak is gone.**
The same fix is worth 0.0014 while the login column is in. Leaks mask each other.
This is the reason leak-hunting is a code review, not an experiment.

</details>

## The promo code, specifically

`promo_code` has 1,500 distinct values across 6,000 rows — a median of four
customers per code. Replacing each code with the mean churn rate of customers who
used it seems reasonable; one-hot encoding 1,500 columns clearly is not.

But with four rows per group, a row's own label is one quarter of its own encoded
value. The column stops being a feature and starts being a compressed copy of the
target.

The measurement:

| How `promo_code` is encoded | ROC AUC, that column alone |
|---|---|
| Target-encoded on the full dataset | 0.7949 |
| Target-encoded inside the CV folds | 0.4899 |

The honest number is *below* 0.5. The promo codes in this dataset were assigned at
random and carry no information about churn whatsoever. The 0.7949 is not weak
signal — it is entirely the learner's own labels being read back to them.

## Common walls

**"I found two."** The third is not in the code. Read the column names and ask the
timestamp question about each one.

**You try to keep `days_since_last_login` by binning or capping it.** The problem
is not its scale or its distribution. The value does not exist at prediction time.
No transformation fixes that. Drop the column.

**You fix the encoding by computing it on the training split only, once, before
cross-validation.** Better, and still wrong: each CV fold then has an encoding
fitted on rows that are in its own validation set. The encoder has to be inside
the pipeline so it is refitted per fold. `sklearn.preprocessing.TargetEncoder`
does the cross-fitting for you when used this way.

**Your fixed score is around 0.86, not 0.75.** You dropped the login column but
the promo encoding is still computed up front. Check the ablation table.

**Your fixed score is above 0.99 and you cannot see why.** Something is still
being fitted on the full dataset. Search your file for `fit_transform` and check
every occurrence — the last checklist item exists for this exact reason.

**Your CV and held-out numbers disagree by a lot after the fix.** That is a
different problem and a real one — usually too small a test set, or a split that
is not stratified. Check your split before assuming another leak.
