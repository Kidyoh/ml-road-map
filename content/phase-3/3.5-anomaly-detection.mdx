      purchase is unusual and fine; a carefully sized fraudulent purchase designed

      matters most. So the unsupervised methods find the tails of the feature

    answer_key: >-
      Contamination sets the threshold on the anomaly score, by telling the
      detector what fraction of the data to declare anomalous. The detector
      computes a continuous score for every point; contamination just picks the
      quantile at which to cut. So it does not change what the model believes, it
      changes how many of the most-suspicious points you choose to act on — set it
      to 0.05 and exactly 5% get flagged, whatever the data looks like. The
      implication is that these methods do not tell you how many anomalies there
      are. They rank, and you decide where to cut, which means the "number of
      anomalies found" is a number you chose rather than a discovery. That is
      worth being blunt about, because the output format encourages the opposite
      reading. The useful consequence is that you should treat the score as the
      real output and pick the cut from capacity or cost, exactly as node 2.4 did
      with the review queue — the top-K framing is more honest here than a binary
      flag.

      dimension. A multivariate method finds points that are unusual in
      combination while being entirely ordinary in every individual column — a
      transaction of a normal amount, at a normal hour, in a normal category, but
      where that particular combination almost never occurs. A small purchase at
      3am in a foreign country from a device that has seen five different cards is
      unremarkable on every axis separately and highly unusual jointly. That is
      the whole reason to bother: in more than a couple of dimensions, most of the

      per-column screening misses the majority of genuinely anomalous points. The

      score does not — and the fix is to keep both, using the univariate rules for

      detector for the cases that only exist jointly.

## Why this node exists

Outliers are three completely different things wearing the same clothes: broken
data, genuine rare events, and the target you are hunting. They produce identical
output from every detector, and the only way to tell them apart is to look at
them.

The reflex to reach for is not "remove outliers". It is "find out what each one
is". Deleting a legitimate extreme value teaches your model that the tail does
not exist — and the tail is often where the decisions are.

## The session

### 1. Three detectors, on data where you know the answer

[`fraud-transactions.csv`](/datasets/fraud-transactions.csv) — 50,000 rows, 222
frauds, rate 0.00444.

```python
IsolationForest(contamination=0.00444, random_state=0)
LocalOutlierFactor(contamination=0.00444)
EllipticEnvelope(contamination=0.00444, random_state=0)
```

Fit each **without the label**. Then, and only then, check what fraction of the
222 real frauds each one caught.

All three will be far behind the supervised model from node 2.4, which reached
about 0.93 PR AUC. Record the ratio. Question 1 asks why this is expected rather
than disappointing.

### 2. The parameter that is not a discovery

Run IsolationForest with `contamination` at 0.00444, 0.01 and 0.05.

The number of flagged points is 222, 500 and 2,500 — which is to say, exactly
what you asked for, every time. The data had no vote.

This is worth internalising: these methods **rank**, and you choose the cut. The
"number of anomalies detected" is your parameter reported back to you.

Better output: keep the scores, sort them, and use the top-K framing from node
2.4.

### 3. Outliers that are a broken machine

[`sensor-readings.csv`](/datasets/sensor-readings.csv) from node 0.5 — 12,000
readings, 532 of them exactly 0.000, all from sensor S-03.

Run a detector. It should find them, because they are genuinely far from
everything else.

Now: is a reading of 0.000 an anomaly to investigate, or a missing value written
as a number? Question 3 asks. The answer determines whether you route it to an
analyst or file a bug against the pipeline.

### 4. Classify twenty by hand

Take twenty flagged points from either dataset and put each in one of three
buckets:

| Category | What it is | What to do |
|---|---|---|
| **Data error** | the measurement is wrong | fix upstream, mark missing, add an indicator |
| **Rare but real** | correct and unusual | keep it — it is the population |
| **The target** | what you were hunting | route it to whoever acts on it |

This is the node. Every detector in existence returns a score; only you can
assign the category.

### 5. One column versus many

Compare a plain `|z| > 3` rule on `amount` against the multivariate detectors.
Find the frauds only the multivariate methods caught, and look at them — they
will be ordinary on every individual axis.

## Which detector assumes what

| Method | Assumes | Struggles with |
|---|---|---|
| z-score / IQR | one column at a time, roughly symmetric | anything jointly unusual |
| EllipticEnvelope | data is a single Gaussian blob | multi-modal or skewed data |
| IsolationForest | anomalies are easy to isolate with few splits | very high dimensions |
| LocalOutlierFactor | anomalies are in locally sparse regions | clusters of differing density |
| Autoencoder | normal data reconstructs well | needs a lot of clean data |

As in node 3.3, choosing a method is choosing an assumption. The sensor data is
bimodal, which is precisely where EllipticEnvelope's single-blob assumption
fails — and it is a good exercise to watch it fail.

## Common walls

**LocalOutlierFactor has no `predict`.** By default it is transductive — it only
labels the data it was fitted on. Set `novelty=True` to get a `predict` for new
data, and note that you then must not call `fit_predict`.

**Everything is flagged as an outlier.** Unscaled features again. Distance-based
methods need node 3.2's treatment.

**Your detector finds the fraud perfectly.** Check that you have not left the
label in the feature matrix. This happens more often than it should and it always
feels great for a few minutes.

**The zeros in the sensor data are not flagged.** They are a spike at a single
value rather than a diffuse tail, and some methods handle that poorly. A value
count catches it instantly where a distance-based detector may not — which is a
good argument for keeping the simple checks from node 0.5 alongside the clever
ones.
