      because shuffling one lets the model lean on its neighbour, so a feature
      measuring near zero may be carrying real signal that another column
      duplicates. Tree models are also fairly robust to irrelevant inputs, so the
      cost of keeping them is small, and a feature that is useless now may matter
      after the population or the data distribution shifts. For dropping: every
      feature is code that must be computed, stored, monitored and kept correct in
      production, and each one is a place where training and serving can disagree.
      Fewer features means faster training, cheaper serving, simpler debugging and
      less to get wrong. What I would actually do: drop them, but by group rather

    answer_key: >-
      A ratio normalises away a scale that is not the thing you care about. Twelve
      transactions means something different for a customer of two months and one
      of two years, so transactions per active month separates behaviour from
      tenure in a way the raw count cannot. Similarly, spend in the last thirty
      days divided by average monthly spend expresses whether someone is
      accelerating or slowing, which is a different quantity from either number
      alone and is often what actually predicts. Linear models especially need
      this, since they cannot construct a ratio from its parts. Where the raw
      count is better: when the absolute magnitude is the decision-relevant thing.
      A customer who has spent fifty thousand pounds matters to the business
      differently from one who has spent fifty, regardless of tenure, and for
      revenue-weighted decisions the total is the point. Counts are also better
      when the denominator can be very small, since a ratio with a denominator of
      one is unstable and generates enormous outliers. The usual answer is to
      provide both and let the model choose.

## Why this node exists

Appendix B is specific about this node: RFM features on transactional data, with
the leakage discipline from node 2.3 carried forward across the cutoff date.

Feature engineering is where most of the achievable improvement on a tabular
problem lives — node 2.7 spent its whole session pointing here. It is also where
leakage is easiest to introduce, because the natural way to write the code
aggregates the whole table, and the whole table includes the future.

Twenty features is enough that you cannot hold the correctness of each one in
your head. That is the point: this node is about building a *structural* defence
rather than a careful one.

## The session

[`retail-events.csv`](/datasets/retail-events.csv), the dataset you framed in
node 2.1. Same cutoff, same population, same label.

| | |
|---|---|
| Cutoff | 2024-10-01 |
| Population | 2,756 customers with pre-cutoff activity |
| Label | transacted on or after the cutoff — 1,550 positive, base rate 0.5624 |
| **Baseline to beat** | **0.8376 ROC AUC**, recency alone |

### 1. The structural guard, first

Before any feature:

```python
pre = df[df.order_date < CUTOFF].copy()
assert pre.order_date.max() < CUTOFF, "pre-cutoff frame contains future rows"

# every feature is built from `pre`. `df` is never touched again.
```

Then go further — make it impossible rather than merely disciplined:

```python
def build_features(frame):
    assert frame.order_date.max() < CUTOFF
    ...
```

**Prove the guard works.** Deliberately pass the unfiltered frame and watch it
fire. A guard you have never seen trip is a guard you do not know is connected.

### 2. Twenty features

Aim for a spread across these families:

| Family | Examples |
|---|---|
| Recency | days since last purchase, days since first |
| Frequency | count, count in last 30/90 days, active months |
| Monetary | total, mean, max, standard deviation of basket |
| Rates | transactions per active month, spend per month |
| Trend | last-30-day spend over average monthly spend, gap between last two purchases |
| Diversity | distinct categories, share in top category, distinct channels |
| Timing | share of weekend purchases, most common hour |

The checklist asks for at least three ratios and at least two describing change
over time. Those are the families people skip, and they are usually the ones that
add something a raw count cannot.

### 3. Measure, do not accumulate

Fit after each family and record the number. A feature that does not move the
score is a feature you are choosing to maintain forever for no reason.

Then permutation importance, on held-out data, per node 2.5. Count how many of
your twenty are indistinguishable from zero. It is usually more than half.

### 4. Build a leak on purpose

Add one of these, measure it, then delete it:

- total spend computed from the full table rather than from `pre`
- number of transactions in the label window
- days until next purchase, measured forward from the cutoff

Watch the AUC jump. Note how good it feels. That feeling is the thing node 2.3
was inoculating you against — question 1 asks how you would have caught it
without knowing.

### 5. The production question

For every feature you keep, answer: **when does this value become known?**

If the answer requires a nightly batch job that has not run yet at prediction
time, the feature is unavailable in production even though it is perfectly
legitimate in training. That is a different problem from leakage and it is just
as fatal.

## The pattern that prevents most leaks

```python
# WRONG - aggregates everything, then filters
features = df.groupby("customer_id").agg(...)
features = features[features.index.isin(population)]

# RIGHT - filters everything, then aggregates
pre = df[df.order_date < CUTOFF]
features = pre.groupby("customer_id").agg(...)
```

The two differ by one line and produce completely different models. The first one
looks fine in review and scores 0.99.

## Common walls

**Your row count is not 2,756.** You have customers with no pre-cutoff activity,
or you built features from `df` rather than `pre` and picked up the extra 24.

**Your ratios have infinities.** Division by an active-month count of zero. Guard
the denominator, and think about whether the guard value you choose is itself
telling the model something.

**A feature adds 0.1 AUC and you are delighted.** Check it. On this dataset,
after recency, nothing legitimate should be worth that much.

**Your rolling-window features are slow.** Groupby-apply over 2,756 groups is
fine; groupby-apply with a Python function over 27,480 rows is not. Use vectorized
aggregations or `pd.Grouper` where you can.

**Permutation importance says everything is unimportant.** Your features are
highly correlated with each other, which is expected for RFM variants. Permute
groups of related features together, or use a method designed for correlated
inputs.
